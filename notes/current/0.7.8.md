# Zopilot 0.7.8 开发计划

最后更新：2026-07-26

## 目标

统一 Codex CLI 和 BYOK 模型的 Zopilot 工具能力。

- 两种后端共用同一个 `/zopilot/mcp` Server。
- `get_outline`、`search`、`read`、`view_page` 只有一份定义和业务实现。
- 两种后端得到一致的文本、页码、图片、状态和错误。
- Codex 自带的搜索、命令和图片查看等工具仍属于 Codex 能力。

## 当前结构

### Codex CLI

`Codex app-server -> /zopilot/mcp -> Zopilot paper tools`

Codex 使用自己的 MCP Client。Zopilot 显式设置只读 sandbox 和
`approvalPolicy: never`。

### BYOK

`BYOK Node runtime -> Agents SDK MCP Client -> /zopilot/mcp -> Zopilot paper tools`

父进程与 BYOK Node 进程之间的 stdio RPC 只负责启动、取消和运行状态，
不再负责调用论文工具。

### MCP Server

- 使用官方 `@modelcontextprotocol/sdk`。
- 使用无状态 Streamable HTTP JSON。
- 每个请求创建并关闭独立的 Server 和 Transport。
- Zotero 层只适配 HTTP、安全 Headers 和日志。
- `PaperToolsService` 位于 application 层，不依赖 Codex 或 BYOK。

### 3. BYOK 图片和 PDF

- [x] 图片附件转换为真实 `input_image`，不再把路径写进 Prompt。
- [x] 本地 PDF 使用 Zopilot PDF Helper 解析。
- [x] PDF 向模型提供检索后的文本、文件名和页码。
- [x] 明确询问图、表、公式或页码时，可附加相关页面图片。

BYOK 也不需要单独实现通用 `view_image`：用户图片通过 `input_image`

### 4. BYOK 图片兼容

- [x] 所有 BYOK Provider 使用相同逻辑，不按品牌或模型名称判断。
- [x] 默认尝试发送图片。
- [x] 接口明确拒绝图片时，隐藏第一次失败过程并自动纯文本重试一次。
- [x] 拒绝结果按 Provider Profile 和模型保存。
- [x] 刷新模型列表时保留拒绝结果。
- [x] Provider Endpoint 改变时清除旧的拒绝结果。
- [x] 图片策略同时控制附件、PDF 页图和 MCP 图片 Header。
- [x] 普通网络、认证、限流、审核和尺寸错误不会被误记为不支持图片。

## 当前问题

### 1. PDF 缓存和构建性能

- 本地 PDF 每次准备时仍会读取完整文件并计算哈希。
- 同一 PDF 的并发构建没有任务复用和锁。
- 旧缓存会先删除，再直接重建。
- 构建中断时可能留下不完整状态。

本地附件解析结果位于：

`<Zotero Profile>/zopilot/materials/local-attachments/<sourceId>/`

Zotero 论文解析结果位于：

`<Zotero Profile>/zopilot/materials/sources/<sourceId>/`

### 2. 工具展开内容仍较通用

工具来源、名称、状态和耗时已经统一，但展开后主要显示通用 JSON。
搜索结果、命令输出、文件 diff 和图片摘要还没有专用组件。

### 3. 尚未支持外部 MCP Server

当前只提供 Zopilot 自己的四个论文工具。还没有外部 Server 管理、
namespace、allowlist、secret、审批和审计。

## 完成标准

- Codex 和 BYOK 只通过 `/zopilot/mcp` 调用 Zopilot 工具。
- 四个论文工具只有一份定义和业务实现。
- BYOK 能读取图片附件、PDF 文本、页码和论文页面图片。
- 不支持图片的 BYOK 接口能自动继续文本对话。
- 工具消息能区分 Zopilot、Codex、状态、错误和耗时。
- 日志、消息和持久化数据不包含 Token 或图片 Base64。
- PDF 缓存构建在并发和取消时保持完整。
